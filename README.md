**سوال 1**

بخش 1

دستور merge تغییرات یک شاخه را با شاخه جاری ترکیب می‌کند و کامیت‌های قبلی را بازنویسی نمی‌کند. اگر دو شاخه پس از جد مشترک، کامیت‌های مستقلی داشته باشند، معمولا یک کامیت ادغام با دو والد ایجاد می‌شود. در نتیجه مسیرهای اصلی توسعه در تاریخچه قابل مشاهده می‌مانند. اگر شاخه جاری هیچ کامیت مستقلی نداشته باشد، ادغام می‌تواند به صورت پیشروی مستقیم انجام شود و در این حالت نیازی به ساخت کامیت ادغام نیست.

برای ادغام یک قابلیت تکمیل شده در شاخه اصلی، پس از بررسی تغییرات، می‌توان از دستورهای زیر استفاده کرد.

git switch main
git merge feature-description

این روش برای شاخه‌های مشترک مناسب است، زیرا شناسه کامیت‌های موجود را حفظ می‌کند و ارتباط شاخه‌ها را در تاریخچه نگه می‌دارد.

بخش 2

دستور rebase کامیت‌های اختصاصی شاخه جاری را روی یک پایه جدید دوباره اعمال می‌کند. در نتیجه معمولا برای کامیت‌های بازاعمال شده شناسه‌های جدید ایجاد می‌شود. این کار تاریخچه را خطی‌تر می‌کند و در حالت معمول کامیت ادغام جداگانه‌ای ایجاد نمی‌کند.

برای به روز کردن یک شاخه محلی که هنوز با دیگران به اشتراک گذاشته نشده است، می‌توان نوشت.

git switch feature-description
git rebase main

در این مثال، کامیت‌های شاخه قابلیت روی آخرین وضعیت main قرار می‌گیرند و تاریخچه خواناتر می‌شود. تفاوت اصلی این است که merge تاریخچه موجود را به هم متصل می‌کند، اما rebase کامیت‌های شاخه را دوباره ایجاد می‌کند و شناسه آن‌ها ممکن است تغییر کند. به همین دلیل، بازپایه گذاری کامیت‌هایی که دیگران بر اساس آن‌ها کار می‌کنند، بدون هماهنگی مناسب نیست.

**سوال 2**

در Git، یک hunk بخشی از تغییرات یک فایل است که به صورت یک واحد نمایش داده می‌شود. با استفاده از Stage تعاملی می‌توان بعضی از بخش‌های تغییر کرده یک فایل را برای کامیت انتخاب کرد، بدون اینکه همه تغییرات آن فایل وارد کامیت شوند.

ابتدا تغییرات فایل README.md را بررسی می‌کنم.

git diff -- README.md

سپس دستور زیر را اجرا می‌کنم.

git add -p -- README.md

گیت هر بخش از تغییرات را نمایش می‌دهد و از من می‌خواهد تصمیم بگیرم که آن بخش وارد Stage شود یا نه. گزینه‌های مهم عبارت اند از:

y: افزودن بخش جاری به استیج

n: رد کردن بخش جاری

s: تقسیم بخش به قسمت‌های کوچک‌تر، در صورت امکان

e: ویرایش دستی بخش و انتخاب دقیق‌تر تغییرات

q: خروج از حالت تعاملی

? : Iنمایش راهنمای گزینه ها


پس از انتخاب بخش‌های مورد نظر، تغییرات آماده شده برای کامیت را بررسی می‌کنم.

git diff --cached -- README.md

برای مشاهده تغییراتی که هنوز وارد Stage نشده‌اند نیز می‌توان نوشت.

git diff -- README.md
git status

در نهایت، اگر محتوای آماده شده دقیقا همان تغییرات مورد نظر باشد، کامیت را ایجاد می‌کنم.

git commit -m "Update README instructions"

این روش کمک می‌کند تغییرات نامرتبط در یک کامیت قرار نگیرند و تاریخچه پروژه منظم‌تر بماند.

**سوال 3**

دستور git bisect برای پیدا کردن کامیتی استفاده می‌شود که باعث ایجاد یک خطا شده است. این دستور با جستجوی دودویی، کامیت‌های بین یک نسخه سالم و یک نسخه معیوب را بررسی می‌کند و معمولا تعداد آزمایش‌های لازم را به میزان قابل توجهی کاهش می‌دهد.

برای مثال، فرض می‌کنم نسخه v1.0 قابلیت ورود کاربران را درست اجرا می‌کند، اما نسخه فعلی دارای خطاست. ابتدا جستجو را آغاز می‌کنم.

git bisect start
git bisect bad HEAD
git bisect good v1.0

گیت یک کامیت میانی را انتخاب می‌کند. در آن نسخه، همان آزمون را اجرا می‌کنم و بر اساس نتیجه به Git اطلاع می‌دهم.

git bisect good

اگر قابلیت در آن نسخه درست کار کند، از دستور بالا استفاده می‌کنم. اگر خطا وجود داشته باشد، به جای آن دستور زیر را اجرا می‌کنم.

git bisect bad

این دو دستور جایگزین یکدیگر هستند و انتخاب آن‌ها به نتیجه آزمون بستگی دارد. Git با دریافت نتیجه، محدوده جستجو را کوچک‌تر می‌کند و کامیت بعدی را انتخاب می‌کند. این فرایند تا پیدا شدن نخستین کامیت معیوب ادامه می‌یابد.

پس از شناسایی کامیت، آن را بررسی می‌کنم و از حالت bisect خارج می‌شوم.

git show <bad-commit>
git bisect reset

در اینجا <bad-commit> باید با شناسه کامیت معیوبی که Git پیدا کرده است جایگزین شود. دستور git bisect reset وضعیت را به شاخه یا کامیت پیش از شروع جستجو برمی‌گرداند و تاریخچه را حذف نمی‌کند.

برای مثال، اگر ۶۴ کامیت بین نسخه سالم و معیوب وجود داشته باشد، جستجوی دودویی تقریبا به ۶ مرحله برای محدود کردن محدوده نیاز دارد. البته تعداد دقیق مراحل به شرایط تاریخچه و آزمون‌ها بستگی دارد.

**سوال 4**

دستور git status وضعیت فایل‌ها را نشان می‌دهد و مشخص می‌کند کدام تغییرات وارد Stage شده‌اند، کدام تغییرات هنوز وارد Stage نشده‌اند و کدام فایل‌ها رهگیری نشده هستند.

برای بررسی تغییرات فایل README.md می‌توان از دستورهای زیر استفاده کرد.

git status
git diff -- README.md
git diff --cached -- README.md

دستور git diff تغییرات وارد نشده به Stage را نمایش می‌دهد و git diff --cached تغییراتی را نشان می‌دهد که برای کامیت آماده شده‌اند.

در سناریویی که فایل‌های tmp هنوز رهگیری نشده‌اند، اگر آن‌ها را با git add وارد Stage نکرده باشم، کامیت معمولی آن‌ها را ثبت نمی‌کند. برای جلوگیری از ظاهر شدن فایل‌های موقت در وضعیت Git، می‌توانم در فایل .gitignore این الگو را اضافه کنم.

/tmp/

این الگو پوشه tmp در ریشه مخزن را نادیده می‌گیرد. سپس فایل .gitignore را ثبت می‌کنم.

git add -- .gitignore
git commit -m "Ignore temporary files"

اگر فایلی از قبل توسط Git رهگیری شده باشد، اضافه کردن آن به .gitignore به تنهایی رهگیری را متوقف نمی‌کند. برای نمونه، اگر فایل tmp/cache.txt قبلا رهگیری شده باشد، می‌توان آن را از شاخص Git خارج کرد، بدون اینکه فایل محلی حذف شود.

git rm --cached -- tmp/cache.txt
git commit -m "Stop tracking temporary cache file"

بنابراین باید بین نادیده گرفتن فایل‌های جدید و خارج کردن فایل‌های قبلا رهگیری شده از شاخص Git تفاوت قائل شد.

**سوال 5**

بخش 1

تعارض ادغام Merge Conflict زمانی رخ می‌دهد که Git نتواند تغییرات دو شاخه را به صورت خودکار با هم ترکیب کند. برای مثال، اگر هر دو شاخه نسبت به جد مشترک، یک خط مشخص از فایل README.md را به شکل‌های متفاوت تغییر داده باشند، Git نمی‌تواند بدون تصمیم گیری مشخص کند کدام نسخه باید در نتیجه نهایی قرار بگیرد.

تغییر یک فایل توسط دو نفر الزاماً تعارض ایجاد نمی‌کند. تغییرات در بخش‌های مستقل یا تغییرات یکسان اغلب به صورت خودکار ادغام می‌شوند. تعارض معمولا زمانی رخ می‌دهد که تغییرات با یکدیگر ناسازگار باشند.

بخش 2

با فرض اینکه روی شاخه main هستم و عملیات ادغام متوقف شده است، ابتدا وضعیت مخزن و فایل‌های حل نشده را بررسی می‌کنم.

git status
git diff --name-only --diff-filter=U
git diff -- README.md

دستور git diff --name-only --diff-filter=U نام فایل‌هایی را نشان می‌دهد که هنوز تعارض حل نشده دارند.

در فایل دارای تعارض، Git معمولا بخش‌های متفاوت را با نشانگرهای زیر مشخص می‌کند.

```text
<<<<<<< HEAD
Content of the current branch
=======
Content of the incoming branch
>>>>>>> feature-description
```

بخش بعد از <<<<<<< HEAD محتوای شاخه جاری، یعنی main، را نشان می‌دهد. علامت ======= دو نسخه را جدا می‌کند و بخش بعد از آن تا >>>>>>> feature-description محتوای شاخه ورودی را نشان می‌دهد.

برای مشاهده دقیق نسخه‌های موجود در یک ادغام معمولی نیز می‌توان از دستورهای زیر استفاده کرد.

git show :2:README.md
git show :3:README.md

در این سناریو، مرحله ۲ نسخه شاخه جاری و مرحله ۳ نسخه شاخه ورودی است.

بخش 3

برای حل تعارض، فایل README.md را باز می‌کنم و محتوای نهایی را طوری تنظیم می‌کنم که اطلاعات مورد نیاز هر دو تغییر حفظ شود. صرف حذف یکی از نسخه‌ها کافی نیست و متن نهایی باید از نظر معنا و نگارش درست باشد.

پس از ادغام دستی، همه نشانگرهای تعارض، یعنی <<<<<<<، ======= و >>>>>>> را از متن نهایی حذف می‌کنم. سپس تغییرات را بررسی می‌کنم.

git diff --check
git diff -- README.md

اگر محتوای فایل درست باشد، آن را وارد Stage می‌کنم تا Git بداند تعارض آن برطرف شده است.

git add -- README.md

پس از آن، تغییرات آماده کامیت و وضعیت تعارض‌ها را بررسی می‌کنم.

git diff --cached --check
git diff --cached -- README.md
git diff --name-only --diff-filter=U
git status

خروجی دستور فهرست فایل‌های حل نشده باید خالی باشد. با این حال، خالی بودن فهرست به تنهایی صحت معنایی متن را تضمین نمی‌کند، بنابراین محتوای نهایی را نیز بازبینی می‌کنم.

در نهایت، ادغام را کامل می‌کنم.

git commit -m "Merge feature-description and combine README changes"
git status

اگر تصمیم بگیرم عملیات ادغام را ادامه ندهم، در صورت امکان و پیش از تکمیل ادغام، می‌توانم آن را لغو کنم.

git merge --abort

این دستور برای لغو عملیات ادغام جاری است و نباید پس از تکمیل موفق ادغام به عنوان روش بازگرداندن کامیت استفاده شود.

**سوال 6**

برای برگرداندن تغییرات، ابتدا باید مشخص کنم تغییرات در چه مرحله‌ای هستند، زیرا روش مناسب برای تغییرات وارد نشده به Stage، تغییرات وارد شده به Stage و کامیت ثبت شده متفاوت است.

بخش 1

اگر تغییرات فایل notes.txt هنوز وارد Stage نشده باشند و بخواهم آن‌ها را دور بیندازم و فایل را به وضعیت آخرین کامیت برگردانم، از دستور زیر استفاده می‌کنم.

git restore --worktree -- notes.txt

این دستور تغییرات محلی وارد نشده به Stage فایل را حذف می‌کند، بنابراین پیش از اجرای آن باید مطمئن باشم که به آن تغییرات نیاز ندارم.

بخش 2

اگر تغییرات فایل قبلا وارد Stage شده باشند، اما هنوز کامیت نشده باشند، می‌توانم آن‌ها را از Stage خارج کنم.

git restore --staged -- notes.txt

این دستور تغییرات فایل را از شاخص Git خارج می‌کند، اما خود تغییرات محلی را نگه می‌دارد. بنابراین برای بررسی یا اصلاح دوباره آن‌ها مناسب است.

بخش 3

اگر یک کامیت اشتباه قبلا روی شاخه مشترک مانند main ارسال شده باشد، معمولا روش امن این است که با دستور git revert یک کامیت جدید بسازم که اثر تغییرات کامیت قبلی را معکوس کند.

برای مثال:

git switch main
git revert abc1234
git push origin main

در این مثال، abc1234 شناسه کامیت مورد نظر است و باید با شناسه واقعی جایگزین شود.

استفاده از git revert تاریخچه قبلی را حفظ می‌کند و کامیت جدیدی برای برگرداندن تغییرات می‌سازد. این روش برای شاخه‌های مشترک مناسب‌تر است، زیرا برخلاف بازنویسی تاریخچه، نیازی به حذف یا تغییر کامیت‌هایی که دیگران بر اساس آن‌ها کار کرده‌اند ندارد.
